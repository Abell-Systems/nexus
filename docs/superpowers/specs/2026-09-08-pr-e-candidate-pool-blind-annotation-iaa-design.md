# PR-E: Independent Candidate Pool, Blind Dual Annotation, IAA Dry-Run

**Status:** Approved design, ready for implementation plan.
**Roadmap anchor:** `docs/roadmap.md` §3, table row **PR-E** ("Blinded re-annotation + IAA dry-run + CPC-auto card"), sequenced before **PR-F** (Phase-2 dataset + DEV/TEST freeze + powered efficacy). PR-E is currently fully unexecuted.

## 1. Purpose

Produce ground-truth relevance judgments that PR-F will later use to evaluate M0/M1/M2, without letting the system under evaluation decide what gets judged. This is a dry-run to validate the *annotation instrument and protocol* — not to estimate efficacy, and not to annotate the full Phase-2 corpus.

## 2. Scope

**In scope:**
- Independent candidate pool generation for a deliberately selected subset of 6–8 demands (of the frozen N=39 Phase-2 corpus), used as a stress test of the protocol — not a statistical sample.
- Frozen semantic embedding artifact for those 6–8 demands, bound to the Phase-2 corpus identity.
- Blind export of the candidate pool (no scores, no retriever identity, no ranking).
- Ordinal 0–3 annotation by two independent annotators (Valentín + Lydia), each blinded to the other's judgments.
- Weighted Cohen's κ + confusion matrix + secondary binary κ (`grade >= 2`).
- Disagreement logging (not resolution).

**Explicitly out of scope (per roadmap "Must NOT include: Phase-2 collection"):**
- Annotating all 39 demands.
- Dev/Test split (PR-F).
- Any M0/M1/M2 efficacy claim.
- Automatic adjudication of disagreements.
- A third/external annotator (deferred to a post-dry-run phase, for adjudication or control sampling only, if κ is acceptable).

## 3. Why an independent pool

If the candidate pool were built from M0/M1/M2's own top-K, annotators would only ever judge what the system already decided was relevant — a selection-bias/circularity that would inflate apparent efficacy in PR-F and make it impossible to distinguish retrieval failure (relevant patent never entered the pool) from ranking failure (it entered but scored low). The candidate pool must therefore be the union of independent first-stage retrieval baselines, eligibility-filtered, with no connection to final ranking.

## 4. Architecture

Reuses existing domain/protocol primitives rather than adding new abstractions — the codebase already models exactly this separation:

- `domain/models/matching.py::CandidatePool` — already documented as "Shared fixed candidate pool (P_shared), constructed strictly as the union of first-stage baselines," with dedup and a 300-candidate structural cap already enforced by the model.
- `domain/protocols/matching.py::PatentCandidateRetriever` — protocol already implemented by `DuckDbBM25Retriever`, `DuckDbCPCRetriever`, and the semantic (M1) retriever in `infrastructure/matching/dense_semantic.py`.
- `infrastructure/matching/eligibility.py::DefaultPatentEligibilityPolicy` — already implements ADR 0018 temporal pool eligibility (`strict`/`unconstrained`).

## 5. Contract rules (from review)

1. `CandidatePoolBuilder` takes `temporal_pool_mode` as an explicit required argument (ADR 0005 explicit-injection pattern, same as `DefaultMatchingAdapter`'s `bm25_k1`/`bm25_b`) — no silent default.
2. Hard boundary at `BlindExport`: everything after it (`AnnotationBatch` and downstream) MUST NOT contain `retrieval_scores`, `RetrievalMethod`, or original ranking/position. Internal `CandidatePool` may retain `retrieval_scores` before the boundary.
3. Shuffle order is deterministic and reproducible: same `blind_export_seed` + same pool → byte-identical export order. Enables regenerating the batch without changing what an annotator saw.
4. CPC-auto card is auxiliary evidence only — contractually not a recommendation, not a score, and must not reveal which retriever(s) surfaced the candidate.
5. Embedding artifact generation is an explicit upstream dependency consumed by the semantic retriever, not a responsibility of `CandidatePoolBuilder`. Contract: "Frozen semantic embedding artifact for the selected Phase-2 dry-run demands, generated with the same pipeline and schema as the pilot artifact (`embeddings_pilot_benchmark.json`), bound to the Phase-2 corpus identity" — not a new experimental dataset.
6. The annotation batch is frozen before either annotator sees any candidate. Annotation judgments MUST NOT modify, expand, filter, or reorder the candidate pool.

## 6. New components

| Component | Layer | Responsibility |
|---|---|---|
| `CandidatePoolBuilder` | `application/evaluation/candidate_pool_builder.py` | Orchestrates the 3 existing retrievers + eligibility policy into one `CandidatePool` per demand. No new domain model. |
| `blind_export.py` | `infrastructure/annotation/` | Enforces the blind boundary; deterministic seeded shuffle; emits `AnnotationBatch`. |
| Annotation guide | `docs/annotation/phase2-guide.md` | 0–3 scale with examples; explicit criteria for the 1↔2 and 2↔3 boundaries. Written before annotation starts. |
| `AnnotationJudgment` | `domain/models/` (new, minimal) | `(annotator_id, demand_id, publication_id) → grade [0-3]`. One frozen, hashed artifact per annotator. |
| `iaa.py` | `application/evaluation/` | Weighted Cohen's κ, confusion matrix, secondary binary κ, disagreement list. |
| Demand selection rationale | `docs/annotation/phase2-dry-run-selection.md` | Documents which 6–8 demands and why (technical diversity, lexical ambiguity, CPC-informative domains, expected BM25/CPC/semantic divergence). |

## 7. Relevance scale

Ordinal 0–3, annotated directly (not derived from binary):

| Grade | Meaning |
|---|---|
| 0 | Not relevant |
| 1 | Marginally relevant |
| 2 | Relevant |
| 3 | Highly relevant |

Primary IAA metric: weighted Cohen's κ (penalizes distant disagreements like 0-vs-3 more than adjacent ones like 2-vs-3). Secondary: binary κ on the derived view `relevant_binary = grade >= 2`, kept only as an additional lens — the ordinal labels remain the source of truth (needed for nDCG@10, PR-F's primary endpoint).

κ is not the sole acceptance criterion — the confusion matrix must also be reviewed for systematic adjacent-level disagreement before deciding the protocol is ready to scale to the full 39 demands.

## 8. Testing

- `CandidatePoolBuilder`: union without duplication, cap respected, eligibility policy applied per explicit `temporal_pool_mode` (most invariants already covered by the existing `CandidatePool` model — new tests target the orchestration, not re-testing the model).
- `iaa.py`: weighted κ against known worked examples; confusion matrix correctness.
- Blindness tests (highest priority):
  - Export contains no `retrieval_scores`.
  - Export contains no `RetrievalMethod`.
  - Export contains no ranking/original position.
  - Same seed + same pool → identical export order.
  - Different seed → same candidate set, potentially different order.
  - Both annotators' exports cover exactly the same `(demand_id, publication_id)` set.

## 9. Exit criteria

If κ is acceptable and disagreements concentrate on understandable adjacent boundaries (1↔2, 2↔3) with no structural ambiguity: freeze the protocol, proceed to scale the same protocol to the full 39 demands (still within Lab track, ahead of PR-F).

If κ is low: do not patch labels. Revisit the guide/label definitions and repeat the dry-run. A third external adjudicator is deferred to this later stage (adjudication or control sample), not introduced now.
