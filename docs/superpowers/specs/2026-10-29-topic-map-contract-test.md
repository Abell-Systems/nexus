# Topic map backend–frontend contract test

Status: proposal, tests written, not yet implemented. Base: `feat/topic-map` (PR #214, draft). Separate PR from the Sonar clean-up.

## Problem

The backend (`build_topic_result`, schema `topic-map/1`) and the frontend (`TopicMapResult` in `domain/topicMap.ts`) each guard their own copy of the schema. Nothing links them. The final review of #214 showed that renaming `ep_documents` to `ep_docs` or turning `trend.share` from percent into a fraction fails one backend test and zero frontend tests.

## Design

One committed, synthetic, deterministic sample is the only thing both sides touch: `contracts/topic-map/1/synthetic-result.json`.

- Outside `docs/whitespace/` and `frontend/public/data/`, so the sync script never discovers it, nginx never serves it, and it does not match the `topic-map-*.json` ignore rules. It is not corpus-derived and the exposure barriers stay as they are.
- Built from the synthetic inputs of `test_topic_map.py` (no OEPM data, D4 untouched).
- Not generated by the build: it is a reviewed fixture. Changing the schema means changing it in the same PR.

### Producer side (pytest)

1. `shouldMatchTheCommittedSampleByteForByteWhenBuiltFromTheSyntheticInputs`: the sample equals the serialised `build_topic_result` output. Any producer change (a renamed field, a unit change, a new field, a different order) fails until the sample is deliberately updated.
2. `shouldPassTheInvariantChecksWhenTheCommittedSampleIsLoaded`: `check_invariants` on the parsed sample, so the sample cannot drift into an impossible state.
3. `shouldDeclareTheSchemaTheFrontendReadsWhenBuildingTheSample`: `schema == "topic-map/1"`.

### Consumer side (vitest)

4. `shouldHaveExactlyTheFieldsOfTheTypeWhenReadingTheSample`: for the root and each nested object (`configuration`, `configuration.parameters`, `corpus`, `topic`, a `trend` row, `top_applicant_recent`, a `subareas` row, a `neighbours` row, a `rare` row, an `applicants` row) the sample's key set equals the key list of the test. The lists are typed `Record<keyof T, true>` against `TopicMapResult`, so the compiler fails if the interface and the lists diverge and the test fails if the sample and the lists diverge. No manual third copy.
5. `shouldHaveTheTypesTheViewsAssumeWhenReadingTheSample`: numbers are finite integers where the views format them, `years` ascending without 2010, `trend` aligned with `years`, `top_applicant_recent.by_year` aligned with `years`, `rare` rows with `observed >= 30` and `ratio < 0.8`.
6. Semantics through the application functions on the sample (no re-implementation in the test):
   - `shouldComputeTheEpShareFromEpDocumentsWhenSummarising`: `periodEpShare` over a period equals `Σ ep_documents / Σ documents` computed from the sample.
   - `shouldReadTrendShareAsPercentWhenDrawingTheChart`: `trend[].share` is within 0..100 and equals `documents / corpus year size` in percent for the sample.
   - `shouldNameTheLeaderOfTheLastTwoYearsWhenSummarising`: `dominantApplicant` equals the applicant with most documents in the last two years of `years`, which is not the all-years leader in the sample by construction.
   - `shouldRenderEveryViewWhenGivenTheSample`: TopicMapPage renders the five hashes from the sample without error and shows no IPC code from `neighbours[].subclass` or `rare[].subclass`.

### Open point for the implementation

`frontend/tsconfig.app.json` includes only `src`, so `npm run typecheck` does not compile tests and the `satisfies Keys<...>` link in test 4 would not run. Proposal: add `test/unit/topicMapContract.test.ts` to `include`. Decide before implementing.

### What this does not cover

Correctness of O4 units, expected counts (E3), applicant rules and reproducibility stay with their own tests and review. Contract compatibility is not mathematical correctness.

## Acceptance

A breaking change on either side fails at least one named test above:

| Change | Fails |
|---|---|
| backend renames `ep_documents` | 1 and 4 |
| backend `trend.share` percent → fraction | 1 and 6 |
| backend `ep_share` fraction → percent | 1 |
| backend adds a field | 1 and 4 |
| frontend type removes or renames a field | 4 (compiler) |
| frontend starts reading a field the producer stopped emitting | 4 and 1 once the sample is updated |

Verified by deliberate breaks in throwaway copies, as in the reviews.
